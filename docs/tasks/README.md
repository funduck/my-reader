# Задачи MVP

Задачи для агентов. Состав MVP и вехи — в [MVP-plan.md](../MVP-plan.md), там же диаграмма Ганта.

## Как работаем

Построчного ревью нет. Задачи ведёт **оркестратор** — одна сессия Claude. Человек проверяет приложение только в контрольных точках `U-1`…`U-7`.

Платформа MVP — macOS. Сборка, `integration_test` и контрольные точки — на Mac. Android — после MVP.

Правила агента, окружение песочницы и принятые решения — в [AGENT.md](AGENT.md).

### Оркестратор

1. Запускает агента (Sonnet) на каждую задачу, у которой все зависимости `done`. Effort агента задаёт явно: `medium` для простых задач (один пакет, понятный контракт), `high` для сложных (несколько пакетов, проводка, сквозные тесты, жесты и платформенные особенности). Другие уровни не использует. Каждый агент — в своём worktree, на ветке `task/<id>`. Одновременно — до 6 агентов.
2. Следит, чтобы каждый пункт «Готово, когда» проверялся командой или тестом. Ручные проверки — только в `U-*`. Принимает результат, только если: `app/scripts/check.sh` или `uv run pytest` зелёный; изменены только пути из «Где»; выполнены все пункты «Готово, когда». Читает тесты: зелёный тест с широким допуском может прятать ошибку. Полную проверку сам запускает один раз — после слияния всех принятых веток волны; упала — ищет виноватую ветку.
3. Не принял — возвращает агенту с конкретным замечанием. После второй неудачи дробит задачу на меньшие или останавливается и пишет человеку.
4. Принятую ветку вливает в `main` и ставит в файле задачи `**Статус:** done`. Конфликты в `bootstrap.dart` разрешает сам, сохраняя обе правки.
5. Когда закрыты зависимости контрольной точки, собирает `flutter build macos` и зовёт человека. Код при этом не ждёт: оркестратор продолжает независимые задачи.
6. Замечания человека из контрольной точки оформляет новыми задачами `T-1xx` в этой папке.
7. Команды, которые в песочнице не работают (см. [AGENT.md — Окружение](AGENT.md#окружение)), передаёт человеку готовой строкой и ждёт результата.
8. Отчёты-документы (`REPORT.md` и подобные) агент возвращает текстом, файл сохраняет оркестратор.
9. Решения из раздела отчёта «Решения для оркестратора» переносит в `DECISIONS.md` затронутого пакета (общие для всех пакетов — в [AGENT.md — Принятые решения](AGENT.md#принятые-решения)) или возвращает агенту. Пункт — одна-три строки: контракт и неочевидное, без пересказа отчёта.
10. Не даёт агенту указаний в обход отказа инструмента или песочницы. Такой отказ — вопрос к человеку.
11. Бриф агенту короткий: id задачи, ветка, какие `DECISIONS.md` прочитать, особенности задачи. Правила из [AGENT.md](AGENT.md) в бриф не копируются: агент читает их сам.
12. После того как изменил статусы или добавил задачи и запушил `main`, запускает `python3 scripts/github_sync.py`. Скрипт копирует `docs/tasks/` и `docs/backlog/` в GitHub: issues, вехи, метки и проект «My reader». Главные — md-файлы, а GitHub только зеркало: правки, сделанные в issues, перезаписываются. Скрипту нужна сеть до `api.github.com`. В песочнице агента её нет, поэтому скрипт запускает только оркестратор.
