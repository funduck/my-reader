# Источники данных: словари, уровни, разметка

Откуда берутся переводы, толкования, уровни слов и выражения для шпаргалки. Требования — в [Requirements.md](Requirements.md), распределение работы между приложением и сервисом — в [Architecture.md](Architecture.md).

## 1. Принципы

1. **Раздаём только данные с открытой лицензией.** Словари с неясным статусом (Мюллер, Апресян и т. п.) не кладём ни в сборку, ни на сервис. Пользователь может импортировать их сам с устройства (P-3).
2. **Сервис хранит полные данные и готовит из них компактные пакеты.** Приложение скачивает пакеты по мере необходимости и работает с ними офлайн.
3. **Тяжёлый NLP — на сервисе, в батче.** На устройстве — только поиск по готовым таблицам.
4. **LLM — не основа, а дополнение.** Её зовут по явному запросу пользователя или когда словари ничего не нашли.
5. **Атрибуция.** Большинство источников — CC BY-SA. В приложении нужен экран «Источники данных», а производные базы распространяются под той же лицензией.

## 3. Словари

### 3.1. Основной источник: Wiktionary (kaikki.org)

kaikki.org публикует разобранный английский Wiktionary в JSONL: одно слово и часть речи — одна строка. В записи есть IPA (`sounds`), часть речи, значения с примерами (`senses`), формы (`forms`) и переводы на другие языки, включая русский (`translations`).

Из одного дампа сервис собирает пакеты:

| Пакет | Содержимое | Режим |
|---|---|---|
| `en-en` | Толкования, IPA, часть речи, примеры | EN → EN |
| `en-ru` | Переводы на русский + IPA и часть речи | EN → RU |
| `en-forms` | Таблица «словоформа → лемма» | Нормализация |

Формат пакета — SQLite с индексом по лемме (и FTS5 для поиска по префиксу). Поиск по индексу укладывается в требование «до 300 мс» с большим запасом.

Ограничение: русских переводов в английском Wiktionary меньше, чем толкований, и они привязаны к значениям неравномерно. Если перевода нет, цепочка провайдеров (P-4) идёт дальше: к пользовательскому StarDict или онлайн-провайдеру.

### 3.2. Пользовательские StarDict-словари

Формат: `.ifo` (метаданные), `.idx` (отсортированный индекс, бинарный поиск), `.dict` или `.dict.dz` (статьи; `.dz` — dictzip, gzip с таблицей чанков для произвольного доступа).

- Приложение на Flutter, поэтому Kotlin/Java-парсеры (QDict и т. п.) не подходят. Парсер пишем на Dart в `lookup_stardict`: формат простой, бинарный поиск по `.idx` — единицы миллисекунд.
- `.dict.dz` при импорте распаковываем в `.dict` один раз, чтобы не реализовывать произвольный доступ к dictzip.
- Статьи бывают в разных форматах (`sametypesequence`: plain text, HTML, XDXF). В модалке показываем их как есть, без разбора на поля T-3.

### 3.3. Онлайн-провайдеры (P-2)

Кандидаты для первой версии:

| Провайдер | Режим | Примечание |
|---|---|---|
| LLM, OpenAI-совместимый API | EN→RU, EN→EN | Учитывает контекстное предложение; один промпт на оба режима |
| DeepL API | EN→RU | Есть бесплатный тариф с ключом |
| Google Cloud Translation / Yandex Translate | EN→RU | Альтернативы DeepL |

В MVP онлайн-провайдеров нет: первыми идут офлайн-словарь Wiktionary и импорт StarDict, см. [MVP-plan.md](MVP-plan.md).

## 4. Уровни слов (T-4, S-3, S-5)

Основа — CEFR-J Wordlist (A1–B2) и Octanove Vocabulary Profile (C1–C2) из репозитория `olp-en-cefrj`. Это CSV: лемма, часть речи, уровень.

Таблица в приложении:

```
lemma | pos | cefr | zipf
```

Правила определения уровня:

1. Словоформу приводим к лемме по `en-forms`.
2. Ищем лемму с частью речи; если часть речи неизвестна — берём минимальный уровень среди вариантов.
3. Если слова нет в CEFR-списке, уровень оцениваем по частотности wordfreq. Пороги Zipf → CEFR подбираем, сверяясь со словами, у которых есть оба значения. Такой уровень помечается как оценка.
4. Иначе — `unknown`.

Объём — ~10–15 тыс. лемм, несколько сотен килобайт. Таблицу можно класть прямо в сборку.

wordfreq больше не обновляется (автор заморозил проект в 2024 году). Для нашей задачи это не мешает: частотность литературной лексики меняется медленно.

## 5. Выражения, фразовые глаголы, лемматизация (S-4)

Тяжёлые ML-модели на устройстве и LLM для базового поиска не используем. Разметку глав делает сервис в батче.

Конвейер на сервисе:

1. **Словарь конструкций.** ~3–5 тыс. фразовых глаголов и идиом из категорий Wiktionary (через kaikki.org) и многословных лемм WordNet. Каждая конструкция хранится как последовательность лемм, например `turn off`, `take into account`.
2. **Разбор текста spaCy:** токены, леммы, части речи, зависимости.
3. **Поиск фразовых глаголов по зависимостям.** Частица связана с глаголом отношением `prt`, поэтому разрывные случаи вроде *turn [the radio] off* ловятся без скользящего окна.
4. **Поиск идиом по леммам** со скользящим окном 1–4 токена и допуском вставок (*take it into account*).
5. **Уровень** каждого слова и выражения — по таблице из раздела 4.
6. **Результат** — разметка главы (диапазоны в тексте + ссылки на записи словаря). Приложение скачивает её и показывает в шпаргалке.

На устройстве (`text_en`) — только лёгкая лемматизация по таблице `en-forms`. Её хватает для T-4 и агрегации H-4. Модели spaCy и тем более Stanford CoreNLP (Java, GPL) в приложение не тянем.

LLM подключается, когда пользователь просит подробное объяснение выражения или когда словари не дали ответа.

## 6. Открытые вопросы

- Пороги Zipf → CEFR: подобрать и проверить на выборке.
- Покрытие русских переводов в Wiktionary: измерить на реальной книге, решить, нужен ли второй открытый EN→RU источник.
- Как часто пересобирать пакеты из дампа kaikki.org и как версионировать их в приложении.
- Нужна ли разметка глав без сервиса (офлайн для книги, которую сервис ещё не обработал) и в каком урезанном виде.
